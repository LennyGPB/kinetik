# Stockage R2 privé

## Configuration

Définir ensemble `R2_BUCKET_NAME`, `R2_ENDPOINT`, `R2_ACCESS_KEY_ID` et `R2_SECRET_ACCESS_KEY` dans `.env` et dans les secrets de l'hébergeur. Redémarrer le serveur après modification. Le SDK utilise `region: auto` et ces identifiants dédiés ; les identifiants AWS de Remotion restent distincts.

Le token doit avoir `Object Read & Write`, limité au bucket concerné. Garder l'accès `r2.dev` désactivé et ne pas attacher de domaine public au bucket. L'application ne change pas ces paramètres Cloudflare. CORS n'est pas nécessaire : les transferts passent par le serveur de l'application.

Une configuration partielle ou invalide échoue explicitement. Une erreur R2 ne déclenche jamais d'écriture sur disque en remplacement. Si les quatre variables sont absentes, le stockage local reste disponible pour le développement.

## Accès aux médias

Les clés et URLs déjà enregistrées restent identiques (`/api/uploads/<userId>/<image|audio>/<fichier>`). Le bucket n'est jamais exposé directement au navigateur.

- L'utilisateur connecté peut lire les fichiers de son propre compte, y compris les uploads non encore attachés à un projet.
- Le lecteur public ajoute `?share=<token>` à ses URLs de médias, y compris les captures spécifiques aux scènes et les zones de focus. Le token autorise seulement les médias du projet partagé, pas les autres fichiers du compte. Ces URLs de partage ne sont jamais enregistrées dans les versions.
- Chaque lecture revérifie le token en base. Désactiver ou renouveler un partage bloque les lectures suivantes, y compris les requêtes partielles audio. Un visiteur sans autorisation reçoit une réponse 404 avant toute lecture R2.
- Les réponses utilisent `Cache-Control: private, no-store` et `Vary: Cookie`. Les copies déjà téléchargées, y compris celles mises en cache avant ce changement, ne peuvent pas être révoquées.
- Claude et Remotion Lambda lisent les fichiers côté serveur via le même driver. Le navigateur et AWS n'ont pas besoin de credentials R2. Les exports Remotion continuent d'intégrer les fichiers dans les props du rendu.

## Quotas et migration

Les quotas de stockage précédents restent actifs : 512 Mio par compte et 2 Gio d'écritures sur 24 heures pour toute l'application. Le calcul par compte utilise toutes les pages de listing R2, inclut les fichiers locaux restants et compte une même clé une seule fois. Les fichiers orphelins sont inclus. Les écritures d'un compte restent sérialisées par Redis.

Commandes (ne jamais afficher les identifiants dans les logs) :

```powershell
node --import tsx --conditions=react-server --env-file=.env scripts/r2-check.ts
node --import tsx --conditions=react-server --env-file=.env scripts/r2-migrate.ts
node --import tsx --conditions=react-server --env-file=.env scripts/r2-migrate.ts --apply
```

Le contrôle crée un petit objet de test et le supprime. La migration commence en aperçu ; `--apply` copie les fichiers, vérifie leur contenu avec SHA-256 et conserve les originaux. Une clé existante identique est ignorée ; un conflit de contenu arrête la migration sans écrasement. Le script peut être relancé après une interruption.

Une lecture cherche d'abord dans R2. Un objet absent peut encore être lu depuis sa copie locale pendant la transition ; une erreur réseau ou d'autorisation R2 reste une erreur. Après migration vérifiée, les copies locales pourront être archivées puis retirées séparément. Aucun nettoyage automatique destructif n'est effectué.

Le listing par compte est adapté au volume initial. À plus grande échelle, un inventaire de fichiers et de tailles en base évitera de lister les objets à chaque upload. La suppression des fichiers orphelins et les politiques de rétention restent à ajouter ; ne pas activer une expiration globale qui supprimerait les médias de projets actifs.

## Tests

```powershell
node --import tsx --conditions=react-server --test lib/storage/access.test.ts lib/storage/r2.test.ts lib/storage/storage.test.ts
```

Les tests vérifient les droits entre comptes, le périmètre des liens de partage, la révocation, les lectures partielles, la validation des clés, la configuration R2, les erreurs et la pagination. Le script `r2-check.ts` vérifie séparément les permissions réelles du bucket.
